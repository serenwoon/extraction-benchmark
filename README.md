# 문서 구조화 벤치마크 — 사람 vs 파이프라인

**장문 문서에서 항목을 뽑아 구조화된 표로 만드는 작업**을, 손으로 했을 때와 파이프라인으로 했을 때로 나눠 잰다.

> 이 저장소의 목적은 도구 자랑이 아니라 **숫자 하나**다 — *"문제 → AI 방식 → 숫자"* 중 마지막 칸.

## 왜 이걸 만들었나

처음부터 AI 에이전트로 일해왔기 때문에 **비교 대상인 "손으로 했을 때"가 존재하지 않았다.**
git 이력을 뒤져봐도 산출량은 나오지만 소요 시간은 안 나온다 — 커밋 간격이 5분~2시간으로 들쭉날쭉하고, 한 커밋에 최대 31개 파일이 한꺼번에 들어오기 때문이다.

그래서 **표본으로 직접 잰다.**

## 방법 — 측정 전에 고정한다 (2026-08-10)

> [!important] 결과를 보고 기준을 바꾸지 않기 위해, 이 절은 **측정을 시작하기 전에** 작성했다.
> 골든셋을 학습에 한 번도 섞지 않는 것과 같은 이유다 — 기준이 결과보다 먼저 있어야 측정이 성립한다.

### 대상 문서

**「대한민국 도로교통법」** (위키문헌, 공개 자료). 조문 **176개**(본칙) / 약 7.4만 자.

**번호가 매겨진 항목이 줄줄이 이어지는 규격 문서**의 전형적인 형태라 골랐다 — 조번호=ID, 조 제목=명칭, 조 본문=세부내용. 그리고 **일과 무관한 공개 문서**라 그대로 공개할 수 있다.

### 표본

`random.seed(20260810)` 으로 **본문 150~900자 대역(135개)에서 10건**을 뽑았다.

- **왜 대역을 제한했나**: 무제한으로 뽑으면 제2조(정의, 3,789자) 같은 이상치가 걸려 그 한 건이 측정 시간의 대부분을 먹는다. 건당 시간을 비교하려면 항목이 서로 비슷해야 한다.
- **왜 시드를 박았나**: 재현 가능해야 하고, 뽑고 나서 마음에 안 든다고 다시 뽑지 않기 위해서다.

> [!warning] 🔴 표본은 **파서 정정 전** 목록에서 뽑혔다 — 시드로 다시 뽑으면 다른 10건이 나온다
> 측정을 끝낸 뒤 파서가 **부칙을 본칙과 같이 세고 있던 것**을 발견해 고쳤다(210 → 176개). 그래서 대역 크기도 135 → 124개로 바뀌었다.
> **측정 자체는 유효하다** — 표본 10건이 전부 본칙이고, 본문도 정정 전후가 글자 단위로 같다(확인함).
> 그래서 **표본을 다시 뽑지 않는다.** 다시 뽑으면 사람이 이미 채운 골든셋을 버리게 되고, 그건 결과를 보고 표본을 고르는 것과 구분되지 않는다.
> 재현하려면 `data/sample_10.json` 을 그대로 쓴다. 파서를 어떻게 고쳤는지는 아래 「파서 정정」 절에 있다.

### 과제

조문 하나당 두 칸을 채운다.

| 칸 | 내용 | 채점 |
|---|---|---|
| **분류** | 5종 중 하나 (`의무`·`금지`·`권한절차`·`정의목적`·`제재`) | **완전일치** |
| **요지** | 40자 이내 한 줄 요약 | 사람이 읽고 판정 (수용/불수용) |

**ID와 명칭은 미리 채워둔다.** 기계적인 옮겨 적기라 판단이 안 들어가고, 그 시간을 빼고 재면 파이프라인 쪽에 유리하게 나오지 않는다 — **의도적으로 보수적인 설계다.**

판정 규칙 4개는 `manual/worksheet.md`에 있다. 이 규칙이 이 저장소의 핵심 자산이다.

### 재는 것

| 지표 | 정의 |
|---|---|
| **건당 소요 시간** | 사람: 타이머 실측 ÷ 완료 건수 / 파이프라인: 실행 벽시계 ÷ 10 |
| **분류 일치율** | 파이프라인 분류가 사람 분류(=골든셋)와 일치한 비율 |
| **불일치 조문** | 갈린 건은 전부 기록한다 — **이게 라벨링 가이드의 재료다** |

### 순서 (중요)

1. **사람이 먼저** 채운다. 파이프라인 출력을 보기 전에.
2. 사람이 끝난 뒤에 파이프라인을 돌린다.
3. 채점한다.

사람이 AI 출력을 먼저 보면 그 순간 측정이 아니라 검토가 된다.

## 한계 — 미리 적어둔다

- **n=10.** 통계적 유의성을 주장하지 않는다. "대략 몇 배"까지가 이 표본이 말할 수 있는 전부다.
- **파이프라인 쪽은 배치 시스템이 아니라 대화형 한 번의 호출**이다. 실제 파이프라인이라면 API 호출·재시도·검증 단계가 붙어 더 걸린다.
- **사람 쪽은 1인 1회**다. 컨디션·숙련도가 섞여 있다.
- **분류 5종은 내가 만든 것**이라, 법학의 표준 분류가 아니다. 재는 대상은 법 해석 능력이 아니라 **기준을 정하고 일관되게 적용하는 작업**이다.

## 결과 (2026-08-10)

| | 사람 | 파이프라인 | 배수 |
|---|---|---|---|
| 완료 건수 | 10 / 10 | 10 / 10 | — |
| 총 소요 | **10분 00초** | **20.5초** (동시 5, 3회 평균) | |
| 건당 | **60.0초** | **2.1초** | **29배** |
| 건당 (순차 환산) | 60.0초 | 8.6초 | **7.0배** |
| 분류 일치 | — (골든셋) | **7~8 / 10** | |
| 요지 40자 규칙 준수 | **2 / 10** | **10 / 10** | |

파이프라인은 조문당 `claude` CLI 를 독립 호출한다. **29배는 병렬 실행 기준, 7배는 순차 환산이다.**
포트폴리오에 쓸 숫자는 **7배** — 보수적인 쪽을 쓴다.

### 파이프라인이 사람보다 나았던 것: 제약 준수

요지 40자 규칙을 **사람은 10건 중 8건에서 어겼고**(평균 52자, 최대 79자), **파이프라인은 3회 실행 30건 중 29건을 지켰다**(평균 32자).
속도 차이보다 이쪽이 더 실무적인 발견이다 — **기계는 명문화된 제약을 지키고, 사람은 내용에 몰입하면 형식을 잊는다.**

### 불일치 3건의 정체 — 2건은 규칙 결함, 1건은 모델 흔들림

같은 입력·같은 프롬프트로 3회 반복해 갈랐다.

| 조문 | 사람 | 파이프라인 | 정체 |
|---|---|---|---|
| RTA-097 (자동차등의 운전 금지) | `금지` | `권한절차` ×3 | **일관된 판단 차이** |
| RTA-163 (통고처분) | `제재` | `권한절차` ×3 | **일관된 판단 차이** |
| RTA-144 (교통안전수칙 제정) | `의무` | `권한절차`×2 / `의무`×1 | **모델 흔들림** |

**두 건의 판단 차이는 같은 모양이다 — 결과 vs 기제.**
사람은 *"이 조문이 있으면 무엇이 일어나나"*(운전이 금지된다 / 범칙금이 부과된다)를 읽었고,
파이프라인은 *"누가 어떤 절차로 하나"*(지방경찰청장의 처분 권한 / 경찰서장의 통고 절차)를 읽었다.

**둘 다 원문을 정확히 읽었다.** 갈린 이유는 판정 규칙 4가 기제 쪽으로 밀고, 규칙 2가 이 경우를 가르지 못하기 때문이다.
→ **어느 쪽의 오류도 아니라 규칙의 결함이다.** 골든셋을 만드는 목적이 정확히 이것을 찾는 것이다.

### 자기일관성 — 같은 입력에 다른 답

10건 중 **8건 안정, 2건 흔들림**(RTA-003 4회 관측 중 1회, RTA-144 3회 중 1회 다른 값).
**단발 실행의 정확도는 그 자체로 신뢰할 수 없다.** 평가 하네스라면 반복 실행과 다수결이 기본이어야 한다.

### 규칙 개정안 — 이 측정이 만들어낸 것

기존 규칙 4가 불이익 처분까지 `권한절차`로 빨아들인다. 규칙 5를 추가한다.

> **5. 행정청이 불이익(금지·제재)을 부과하는 조문은, 절차 서술이 있더라도 그 불이익의 성격(`금지`/`제재`)으로 분류한다. 규칙 4는 의무·급부 절차에만 적용한다.**

다음 라운드는 이 규칙으로 다시 잰다. **개정 전 결과를 지우지 않고 같이 남긴다** — 규칙을 바꿔서 점수가 올라간 것인지 구분할 수 있어야 하기 때문이다.

# 두 번째 측정 — 단서는 요약에서 사라진다

첫 측정이 **속도**를 쟀다면 이건 **누락**을 잰다. 새 작업을 시키지 않고, 위에서 이미 모은 답을 다른 각도로 봤다.

## 왜 이걸 쟀나

규격 문서의 항목에는 본문을 **한정하거나 뒤집는 단서**가 붙는다. 본문만 읽고 단서를 흘리면 **결론이 정반대로 간다.**
실제로 그런 사고를 본 적이 있다 — 본문이 요구하는 것과 단서가 요구하는 것이 반대였고, 본문만 읽은 해석이 그대로 산출물에 들어갔다.

**그러면 얼마나 흔한 문제이고, 요약은 그걸 얼마나 살려내는가?**

## 얼마나 흔한가

| 판정 기준 | 단서 포함 항목 |
|---|---|
| 괄호 포함 (느슨) | 59 / 176 (34%) |
| **괄호 제거 (기준)** | **50 / 176 (28%)** |
| 「다만,」만 (보수) | 47 / 176 (27%) |

`(광역시의 군수는 제외한다)` 같은 **정의용 괄호**는 본문을 한정하는 단서가 아니다. 그냥 `제외한다`로 세면 이런 것까지 걸려 숫자가 부푼다.
→ 괄호를 지우고 센 **28%**를 쓴다. **기준을 바꿔도 27~34% 안에 있다.**

표본 10건 중 단서를 가진 것은 **4건**이고, **세 기준 모두 같은 4건**을 가리킨다.

## 요약이 그 단서를 살려냈는가

| | 단서 반영 |
|---|---|
| 사람 요약 | **0 / 4** |
| 파이프라인 요약 (3회) | **0 / 4 · 1 / 4 · 1 / 4** |
| **기계 스캔** | **4 / 4** (정규식 한 줄, 176개 전수 0.0초) |

파이프라인이 한 번 잡은 것도 *"…절차와 **예외**를 정한 조문"* 이라는 **한 단어**였다. 무엇이 예외인지는 없다.

### 세 줄 공식으로

> **문제**: 규격 문서 항목의 **28%**에 본문을 한정하는 단서가 붙어 있는데, 요약하면 사라진다. 흘리면 결론이 반대로 간다.
> **방식**: 요약과 **별개로** 단서 신호를 기계적으로 스캔해 항목마다 플래그를 붙였다.
> **숫자**: 단서 반영률 사람 **0/4** · LLM **0~1/4** → 기계 스캔 **4/4**. 전수 검사 0.0초(176개).

## ⭐ 이 측정의 진짜 결론 — 더 나은 요약기가 답이 아니다

사람도 LLM도 **똑같이 흘렸다.** 그러니 이건 요약기의 성능 문제가 아니다.

> **40자 안에 본문과 단서를 다 담는 것은 물리적으로 어렵다.**
> 요약의 결함이 아니라 **요약이라는 형식의 한계**다.

그래서 답은 "요약을 더 잘하게 만든다"가 아니라 **"요약 옆에 단서 칸을 따로 둔다"** 이다.
기계 스캔은 판단을 하지 않는다 — **"여기 단서가 있으니 사람이 보라"**고만 말한다. 그거면 충분하다.

### 두 측정이 서로 맞물린다

| | 40자 제약이 한 일 |
|---|---|
| 첫 측정 | **미덕** — 기계는 지켰고(10/10) 사람은 어겼다(2/10). 형식이 곧 품질인 산출물에서 자동화의 값어치 |
| 두 번째 측정 | **비용** — 그 40자가 단서를 잘라냈다. 양쪽 다 |

**같은 제약이 한쪽에선 미덕이고 다른 쪽에선 비용이다.** 제약을 없앨 게 아니라, 제약 때문에 잘리는 것을 **다른 칸에서 받아야 한다.**

## 한계

- **`REFLECT` 판정이 거칠다.** 요약에 `다만/예외/제외/단서` 같은 낱말이 있는지로 기계 판정했다. 후하게 잡아준 기준인데도 최대 1/4이다 — 엄밀하게 보면 더 낮다
- **n=4.** 표본 10건 중 단서를 가진 것이 4건뿐이다. 비율(28%)은 176건 전수라 단단하지만, 반영률 쪽은 표본이 작다
- **표본이 단서 쪽으로 조금 치우쳤다.** 말뭉치의 단서 비율은 28%인데 표본에서는 **40%**(4/10)다. 우연이고, 표본이 작을 때 흔한 일이다
- **단서가 다 중요한 것은 아니다.** 28% 중 실제로 결론을 뒤집는 것이 몇 %인지는 아직 안 쟀다. 다음 라운드 과제

# SQL로 다시 재기 — 그리고 파서 정정

측정 기록이 JSON 파일 일곱 개에 흩어져 있어서, *"실행별로 나눠 보기"*나 *"단서가 있는 항목만 골라 보기"* 같은 질문에 매번 스크립트를 새로 짜야 했다. 조인 한 번이면 되는 일이다.
→ SQLite 로 적재하고([`sql/schema.sql`](sql/schema.sql)) 질문 일곱 개를 쿼리로 썼다([`sql/analysis.sql`](sql/analysis.sql)). 결과는 자립형 대시보드로 굽는다([`dashboard/index.html`](dashboard/index.html)).

설치할 것은 없다. 파이썬 표준 라이브러리의 `sqlite3` 만 쓴다.

```bash
python sql/load.py && python sql/build_dashboard.py
```

## 🔴 스키마를 선언하니 데이터가 틀렸다는 게 드러났다

`article.id` 에 `PRIMARY KEY` 를 걸자 **적재가 즉시 실패했다.** 중복 ID가 있었다.

원인: **부칙을 본칙과 같이 세고 있었다.** 부칙은 조 번호가 1부터 다시 시작한다(시행일·경과조치). 그래서 「제3조」가 여섯 개였다.
추가로 제84조는 개정 전·후 두 판본이 실려 있었다 — 원본 문서의 특성이지 파서 버그는 아니다. 마지막(최신)을 채택하고, **무엇을 버렸는지 찍게** 했다.

| | 정정 전 | 정정 후 |
|---|---|---|
| 항목 수 | 210 (부칙 37 포함, 중복 34) | **176** (본칙, 중복 제거) |
| 단서 비율 (기준) | 58/210 = 28% | **50/176 = 28%** |

> **결론은 바뀌지 않았다** — 비율이 28%로 같고, 기준을 바꿔도 27~34% 안에 있다. 표본 10건도 전부 본칙이라 측정은 그대로 유효하다.
> 그래도 **항목 수는 틀린 값이었다.** JSON 파일로 두는 동안 아무도 물어보지 않았고, **제약을 하나 선언하자 1초 만에 드러났다.**
> 느슨한 자료구조는 틀린 데이터를 조용히 품는다. 이게 이 저장소가 계속 마주치는 같은 주제다.

## SQL이 새로 알려준 것 셋

**1. 다수결은 정확도를 안 올린다** *(Q3)*
반복 실행 + 다수결을 기본으로 하자던 결론을 실제로 계산해봤다. 일치율은 **70%로 그대로**였다. 표가 갈린 항목이 1건뿐이고 거기서 다수결이 고른 답이 사람과 달랐기 때문이다.
→ 반복 실행이 주는 것은 **정확도가 아니라 재현성**이다. 흔들림을 판단 차이로 오해하는 일을 막아준다. 그것만으로 충분한 이유지만, **효과를 정확히 이름 붙여야 한다.**

**2. 오류가 한 방향으로만 난다** *(Q4 혼동 행렬)*
사람이 무엇이라 했든 기계는 `권한절차`로 몰았다 — 금지 3/3, 제재 3/3이 전부 그리로. 무작위 오류가 아니라 **판정 규칙이 절차 쪽으로 기울어 있다는 신호**이고, 규칙 5가 겨냥한 지점을 데이터가 확인해준다.

**3. 위험 항목을 대리지표로 뽑으려 했는데 실패했다** *(Q7)*
모델 흔들림 · 요지 길이 초과 · 단서 유무를 더해 위험점수를 만들어봤다. **실제 불일치와 안 맞는다** — 3점짜리는 일치했고 불일치 3건은 2·1·1점이다.
→ **확신도는 대리지표로 때울 수 없고 사람에게 직접 물어야 한다.** 실패한 가설이라 더 값지다. 대시보드에 그대로 남겼다.

**부수적으로**: 본문 길이와 호출 시간은 무관했다 *(Q6 — 짧은 절반 9.0초 / 긴 절반 8.2초)*. 비용을 입력 길이로 추정하면 틀린다.

## 재현

```bash
python scripts/parse_law.py data/raw.html data/articles.json
python scripts/make_worksheet.py
python scripts/timer.py start   # 사람 작업 시작
python scripts/timer.py stop    # 사람 작업 종료
python scripts/run_pipeline.py --workers 5      # 파이프라인 (반복 시 --tag _r2)
python scripts/score.py                          # 첫 측정 채점
python scripts/clause_check.py                   # 두 번째 측정
python sql/load.py && python sql/build_dashboard.py   # SQL 적재 + 대시보드
```

원본 HTML은 `data/raw.html`에 그대로 넣어뒀다. 위키문헌은 갱신되므로, 재현하려면 이 파일을 쓴다.
